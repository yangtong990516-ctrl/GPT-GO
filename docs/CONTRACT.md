## 4. 包结构规范（用户明确）

- 每一个模块 = 一个独立的 package，包结构必须清晰。
- 遵循 Go 标准分层：

| 目录 | 职责 |
|------|------|
| cmd/server/ | 程序入口（main） |
| internal/apiserver/ | HTTP 路由层（对外 API） |
| internal/service/<模块>/ | 业务逻辑（每个业务模块一个子包） |
| internal/store/<模块>/ | 存储层（Mongo / 文件） |

| pkg/ 或 internal/util/ | 通用工具类（见第 5 条） |
| docs/ | 迁移文档（含本契约） |

- 环境兼容本机 Go 语言环境（当前 Go 1.24.13）即可，不强制引入更高版本特性。

## 5. 通用工具类（用户明确，不可漂移）

> 通用能力必须抽到工具类统一调用，禁止在各模块重复实现。

必须进入工具类（internal/util/ 或 pkg/）的能力，包括但不限于：

| 工具 | 职责 | 统一调用点 |
|------|------|-----------|
| HTTP 客户端 | 发起 HTTP 请求（GET/POST/…）、超时、代理、重试、TLS 指纹 | util.NewHTTPClient() / util.Do() |
| 创建请求 | 统一构造 request（header、body、query、代理注入） | util.NewRequest() |
| JSON 序列化 | 统一 camelCase / null 语义 / 严格解析 | util.Marshal() / util.Unmarshal() |
| 错误到HTTP映射 | 统一错误类型到状态码 + {code,message} | util.HTTPError() |
| 日志 | 统一日志器 | util.Logger() |
| 配置加载 | YAML 读取与校验 | config.Load()（或 util 内） |
| 时间/时区 | UTC 统一、ISO 序列化 | util.NowUTC() 等 |

规则：任何模块需要上述能力时，只能调用工具类，不得自己再写一份 HTTP 客户端、请求构造、JSON 处理等。
若发现重复实现，视为违反本契约，须重构为工具类调用。

> 以上工具类清单与命名在本文件固定；后续若新增通用能力，必须同步更新本文件后才能在代码中使用。

## 6.5 代码质量与 Go 惯用法（用户明确，不可漂移）

### 6.5.1 总原则与优先级

迁移必须同时满足：

1. **行为等价**：保持已确认的输入输出、状态变化、错误行为、副作用与协议行为。
2. **Go 惯用实现**：根据语义重新组织代码，使用清晰的类型、错误处理、资源管理与并发模型。
3. **合理效率**：避免明显浪费；进一步优化必须有依据。

**功能正确不代表代码合格；写得“像 Go”也不能成为改变行为的理由。**

出现冲突时，按以下顺序处理：

> 已确认的行为契约与安全边界 → 正确性和资源生命周期 → 可读性和可维护性 → 有依据的性能优化。

没有用户授权，不得以重构、简化、并发化或性能优化为由改变外部行为。发现原实现疑似有 bug，应单独记录；不得在迁移中悄悄修复。

### 6.5.2 实现前：先提炼语义，禁止逐行翻译

每个模块开始迁移前，必须先明确：

- **输入与输出**：字段类型、可选性、默认值、返回结构。
- **状态与所有权**：哪些状态属于单次调用、任务、会话或全局；由谁创建、修改、释放。
- **副作用**：网络请求、文件写入、数据库修改、缓存更新等。
- **失败语义**：错误分类、重试条件、取消行为及部分成功的处理。
- **顺序要求**：请求、回调、结果和状态更新是否必须保持顺序。
- **兼容边界**：哪些行为必须保持，哪些内部实现可以重构。

据此设计 Go 的类型、函数边界和执行流程，再写实现。

**禁止事项：**

- 按 Python 源文件逐行生成对应 Go 代码。
- 为保留原代码形状，照搬动态类型判断、异常捕获和临时字典。
- 未理解调用关系，就将 Python 类一律转换为 Go struct。
- 将原本串行的操作直接改成并行，却不验证顺序、状态及副作用。

普通算法在两种语言中结构相似并不自动构成问题；必须检查其类型表达、职责划分和生命周期是否符合 Go 习惯。

### 6.5.3 类型与数据建模

#### 必须遵守

1. 业务结构已知时，优先定义明确的 `struct`、字段类型及必要的方法。
2. 核心业务流程不得长期依赖 `map[string]any` 和反复类型断言。
3. 动态输入应在入口完成解析、校验和规范化，再交给类型明确的内部函数。
4. 明确区分：
   - 字段缺失；
   - 显式 `null`；
   - 空字符串或空集合；
   - 数值 `0`；
   - 布尔值 `false`。
5. 按行为要求选择零值、指针、自定义可选类型或额外的存在标记。
6. 如果“缺失”和“显式 null”也需要区分，不能认为一个指针字段就一定足够。

#### 禁止事项

- 为方便迁移，将大量函数参数和返回值定义为 `any`。
- 在已经确定类型的内部流程中反复做“以防万一”的类型判断。
- 未核对语义，就将 Python 的 truthy/falsy 默认值逻辑直接替换为 Go 零值。
- 用同一个巨大 struct 同时承载配置、运行状态、请求数据和响应数据。

#### 必须关注的兼容细节

- JSON 字段省略与输出 `null` 的区别。
- `nil` 切片与空切片在序列化时的区别。
- 数字范围、精度、溢出和类型转换。
- Python 保留插入顺序的字典与 Go map 遍历顺序的区别。
- 字符串按字节、Unicode 码点或其他规则处理的区别。

这些差异必须按实际业务契约处理，不能依赖语言默认行为碰巧一致。

### 6.5.4 错误处理

#### 必须遵守

1. 可预期的失败通过 `error` 返回。
2. 调用方需要区分的错误，使用哨兵错误或明确的错误类型。
3. 使用 `errors.Is` / `errors.As` 判断错误，保留错误链。
4. 需要增加上下文时，使用 `fmt.Errorf("操作信息: %w", err)`。
5. 新增上下文必须提供有效信息，例如操作、对象或阶段；不得每层重复包装同一句话。
6. 外部错误码、响应格式和约定文案由边界层统一映射，避免内部包装改变对外契约。
7. 仅在能够处理、转换或增加有效上下文的地方处理错误，否则直接返回。

#### 禁止事项

- 用 `panic/recover` 模拟 Python 的常规异常处理。
- 使用 `err.Error()` 字符串比较判断内部错误类型。
- 吞掉错误并返回成功、空结果或默认值。
- 忽略可能影响正确性的错误返回值。
- 每层都记录同一个错误，再继续向上返回，造成重复日志。

确需忽略错误时，应能说明原因及影响。资源关闭错误不能一律忽略，也不能覆盖更重要的原始错误。

### 6.5.5 接口、函数边界与重复逻辑

#### 接口与解耦

- 当需要替换实现、隔离外部依赖或表达稳定能力边界时，定义小接口。
- 接口通常由使用方按实际需要定义，避免包含调用方不使用的方法。
- 不需要多态的简单逻辑可以直接使用具体类型。
- 多态行为优先通过接口和方法集表达，避免散落 `if type == ...` 或类型开关。
- 对协议字段、状态或操作类型进行分派时，常量和 `switch` 是合理做法，不应强行改成接口体系。

**禁止为了“使用接口”给每个 struct 配一个接口。**

#### 函数与职责

- 一个函数应承担清晰的主要职责。
- 优先使用提前返回降低嵌套层级。
- 将可独立理解、验证或复用的逻辑拆分为函数或方法。
- 配置项过多且含义不同，应考虑配置 struct，避免冗长的位置参数和难以理解的多个布尔参数。
- 不为简单逻辑建立多层转发、工厂或通用框架。

#### 消除重复

同一业务规则、解析规则、错误映射或资源操作出现两次及以上时，必须检查是否存在重复维护风险：

- **语义相同、应同步变化的逻辑：必须抽取。**
- **只是语法相似、业务含义不同的逻辑：不得强行合并。**

抽取后不得通过大量布尔开关、类型判断或 `any` 参数维持不同分支。

Go 中应使用职责明确的函数、方法或包组织共享逻辑，不以“工具类”作为默认设计方式。

### 6.5.6 资源生命周期、context 与并发

#### 资源管理

- 资源创建成功后，应尽早确定释放路径。
- 函数拥有且需要在函数结束时释放的资源，优先使用 `defer`。
- 明确 HTTP Response.Body、文件、连接、事务、计时器及原生引擎对象的所有权。
- 返回流、连接或其他资源时，必须明确调用方的关闭责任。
- 不得在长循环内不断累积 `defer`，导致资源直到整个函数返回才释放；应缩小作用域或及时关闭。
- 借用的资源不得擅自关闭；转交所有权的资源不得提前关闭。

#### context

- 可能阻塞、执行 IO 或持续较长时间的操作，应接收并传递 `context.Context`。
- 通常将 `ctx` 作为第一个参数。
- 超时应从调用方 context 派生，正确调用派生 context 的取消函数。
- 不得在调用链中使用 `context.Background()` 替换传入的 context，切断取消传播。
- 不将请求级 context 随意存入长期存活的对象。
- 不将 context 当作普通参数容器或全局配置容器。
- 取消必须覆盖实际阻塞点，而不只是函数入口检查一次。

#### 并发

只有在工作可以并行、共享状态可控且行为允许时，才引入并发。

每组 goroutine 必须明确：

1. 谁创建；
2. 谁取消；
3. 如何等待退出；
4. 如何传递错误；
5. 如何限制并发数量；
6. 如何保护共享状态；
7. 谁负责关闭 channel。

按用途选择机制：

- 数据传递和协调：channel；
- 共享状态保护：mutex 等同步原语；
- 等待完成：WaitGroup 或适合的任务组；
- 简单同步操作：直接调用，无须 goroutine。

**禁止事项：**

- 无界创建 goroutine。
- 启动后无人等待、无人取消。
- 向同一个 map 无保护地并发写入。
- 并发修改共享客户端、代理配置或请求对象。
- 将非并发安全的 JS Runtime、原生句柄等共享给多个执行者。
- 将 Python 的 `asyncio.gather` 机械替换成若干 goroutine，却不处理取消、错误和退出。
- 以提高吞吐为由，破坏原有会话隔离、顺序或重试语义。

### 6.5.7 性能与实现简洁性

#### 必须避免的明显低效

- 已知且可信的容量，优先合理预分配 slice / map。
- 避免在循环中重复解析不变配置、编译相同正则或构造昂贵对象。
- 避免无意义的字符串、字节切片、JSON 和中间集合转换。
- 大数据传输在行为允许时优先流式处理。
- 使用适合语义的内建操作，如 `append`、`copy`、`range`，避免重复实现已有能力。
- 有限资源必须有明确上限和释放策略。

容量来自外部输入时，必须先校验范围，不能按不可信值直接进行大规模分配。

#### 优化边界

- 不追求“完全没有循环”或“完全没有分配”。
- 不因语言特性存在就强行使用。
- 不在没有依据时引入 `unsafe`、复杂对象池、锁自由结构或难以维护的缓存。
- 只有测量或明确的复杂度分析支持时，才声称实现更快或更省内存。
- 优化必须保持输出、错误、副作用和资源生命周期正确。

### 6.5.8 每个模块的强制 review 与完成门槛

每个模块迁移完成后，必须主动进行一次 Go 惯用法 review，修正发现的问题，再报告完成。

Review 至少检查：

- [ ] 行为契约、边界值和副作用是否保持。
- [ ] 是否存在机械直译、动态字典滥用或多余类型判断。
- [ ] 是否正确区分缺失、null、空值、0 和 false。
- [ ] 错误是否可识别、可追踪，是否存在吞错或重复日志。
- [ ] 接口和函数划分是否必要、清晰，是否存在过度设计。
- [ ] 同一业务语义是否存在重复实现。
- [ ] 所有资源是否有正确释放路径。
- [ ] context 是否传到实际 IO 和阻塞点。
- [ ] goroutine 是否有数量上限、退出路径和等待机制。
- [ ] 共享状态、会话和非并发安全对象是否正确隔离。
- [ ] 是否存在明显重复分配、不必要复制或重复计算。
- [ ] 注释是否解释约束和原因，而非复述代码。

#### 验证要求
